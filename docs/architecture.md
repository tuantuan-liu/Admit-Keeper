# 架构

## 角色划分

```
┌───────────────────────────────────────────────────────────┐
│  准入裁定层（插件 · pre_gateway_dispatch 钩子）          │
│  同步 / 热路径 / 只读                                       │
│  每条消息进网关 → 判「谁有资格进入」→ skip 则丢弃          │
└──────────────┬────────────────────────────────────────────┘
               │ 只读
               ▼
        ┌─────────────────────┐
        │  admit_keeper.db     │   ← 唯一共享数据层（SQLite，WAL）
        │  admit_allowed 表     │      platform + identity + status + expires_at
        └──────────────┬──────┘
               │ 读写
               ▼
┌───────────────────────────────────────────────────────────┐
│  授权管理层（MCP server）                                    │
│  异步 / 低频 / 读写                                          │
│  grant/ban/unban/extend/query/get_expired/list/remove      │
└───────────────────────────────────────────────────────────┘
```

- 插件 = 准入面：每条消息进网关判定，只读库。
- MCP = 管理面：动态授权 / 封禁 / 续期 / 查询/列举，读写库。
- 职责单向：MCP 写、插件读，互不入侵，靠同一个 SQLite 解耦。

## 决策逻辑集中化

判定语义（banned > 过期 > 无记录 > 白名单）统一收在
`admit_keeper/policy.py:decide()`，插件与 MCP **共同 import 同一份**。
源码上只有一处实现，避免两侧判词漂移。数据读写收在 `admit_keeper/db.py`。

## 为什么用插件而不是改源码补丁

| | 补丁 adapter | 插件（推荐） |
|---|---|---|
| `hermes update` 后 | 被打回，需重打 | 无感，永不失效 |
| 到期封禁 | 实时 | 实时（钩子每条消息都跑） |
| 是否改源码 | 是 | 否，纯插件目录 |
| 维护 | 每次升级重打 | 一次装好，不管 |
| 风险 | — | 默认 fail-open，与无插件时一致 |

## 准入触发点

钩子挂在 `gateway/run.py` 的 `pre_gateway_dispatch`，位于各平台 adapter
（如 feishu `_admit()` 平台白名单）**之后**——消息先过平台白名单，才进准入钩子。
因此采用：

| 设计 | 效果 |
|------|------|
| A（推荐）：`FEISHU_ALLOW_ALL_USERS=true` + 插件当唯一门卫 | 只写 DB 即实时生效，维护量零 |
| B：`allow_all=false` + 改 `FEISHU_ALLOWED_USERS` | 每次动 env + 重启网关，维护高 |

选 A——把「全体放行」收紧成「只有 DB 活跃用户或白名单可见」，安全更好。

## 数据层

SQLite，`PRAGMA journal_mode=WAL` + `busy_timeout`，插件热路径只读、
MCP 写路径低频，读写锁冲突概率低。DB 为一单一来源，无外部服务。
